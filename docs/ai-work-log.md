# Журнал работы с ИИ — Kvarta

## 1. Цель проекта

Создать сайт для кофейной обжарки Kvarta, который знакомит посетителей с ассортиментом кофе, ценами, условиями подписки, доставки и самовывоза. Также необходимо реализовать форму заявок и опубликовать работающий сайт в интернете.

## 2. Как использовался ИИ

ИИ использовался как вспомогательный инструмент при разработке и настройке проекта:

- Получение рекомендаций по реализации сайта на Java и Spring Boot.
- Помощь с настройкой Git и публикацией исходного кода на GitHub.
- Подготовка Dockerfile для сборки и запуска Spring Boot-приложения.
- Пошаговая настройка развёртывания приложения на Render.
- Подготовка README.md с описанием проекта, используемых технологий и инструкцией по запуску.
- Помощь с оформлением мобильного Lighthouse-отчёта в репозитории.

ИИ использовался для ускорения решения технических задач, но его рекомендации требовали проверки и выполнения в реальной среде разработки.

## 3. Что было сделано самостоятельно

В процессе работы я использовал IntelliJ IDEA для работы с проектом, настраивал Git и GitHub, выполнял коммиты и отправлял изменения в удалённый репозиторий.

Я участвовал в настройке Dockerfile и развёртывании приложения на Render, проверял доступность опубликованного сайта и работу формы заявки. Также подготовил README.md и провёл проверку сайта с помощью Google PageSpeed Insights, сохранив мобильный Lighthouse-отчёт в репозитории.

## 4. Ошибки и ограничения при использовании ИИ

В ходе работы стало понятно, что инструкции ИИ не всегда учитывают текущее состояние проекта. Например, после того как сайт и форма уже работали, рекомендации продолжали предлагать повторную проверку этих функций.

Я уточнял состояние проекта и корректировал дальнейшие шаги, чтобы не тратить время на повторные действия.

Также я учитывал, что успешный запуск приложения на Render сам по себе не гарантирует постоянное хранение данных. Файловая база H2 может потерять данные при перезапуске или повторном развёртывании сервиса на бесплатном тарифе.

Этот опыт показал, что ответы ИИ нужно сопоставлять с реальным состоянием приложения, проверять инструкции на практике и не считать предложенное решение правильным без проверки.

## 5. Что осталось улучшить

В дальнейшем я бы уделил больше внимания следующим задачам:

- Проверка валидации телефонных номеров на различных входных данных.
- Проверка защиты от повторного создания заявок с одним номером телефона в течение 10 минут.
- Проверка сохранности заявок после перезапуска приложения.
- При необходимости — перенос данных в PostgreSQL с постоянным хранением.
- Дополнительная оптимизация мобильной версии на основании результатов Lighthouse.
- Возможное добавление уведомлений о новых заявках в Telegram.

## 6. Итог

В результате работы создан и опубликован сайт Kvarta, исходный код размещён на GitHub, а приложение развёрнуто на Render.

В процессе выполнения задания я получил практический опыт работы с Git, Docker, облачным развёртыванием Spring Boot-приложения и проверкой качества веб-страниц. Использование ИИ помогло разобраться с техническими вопросами, а практическая проверка позволила оценивать результат, а не только следовать рекомендациям.
